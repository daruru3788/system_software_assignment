# 구현과 검토 기록

## 개발 목표와 설계 선택

이 구현의 핵심 과제는 명령어 한 줄을 숫자로 바꾸는 일과 프로그램 전체의 주소를 맞추는 일을 함께 처리하는 것이었다. 특히 가상명령의 확장 길이, 뒤에 정의된 라벨, 섹션 사이의 정렬이 서로 영향을 주므로 각 단계를 나누고 단계 사이의 조건을 확인했다.

| 설계 선택 | 해결하려는 문제 | 현재 코드에서의 적용 |
|---|---|---|
| 주소 배정과 바이트 생성 분리 | 전방 참조를 처리하면서 분기·데이터 주소를 확정해야 함 | `layout_sections()` 이후 `generate_image()` 실행 |
| 기존 인코더를 호출하는 변환 단계 | 가상명령마다 비트 조립을 다시 구현하면 같은 규칙이 여러 곳에 생김 | `instruction.cpp`에서 실제 명령으로 변환하고 형식별 인코더 호출 |
| 크기 계산과 생성 결과 대조 | `li` 확장 길이가 달라지면 뒤 라벨의 주소가 어긋남 | 예약한 `byte_size`와 실제 생성 바이트 수를 비교 |
| 실제 주소로 정렬 계산 | 섹션 시작을 0으로 가정하면 큰 정렬 경계에서 오차가 생길 수 있음 | text·data·bss 시작 주소를 정한 순서대로 `.align` 계산 |
| 소스 검증 완료 후 출력 | 잘못된 입력이 이전의 정상 결과를 덮어쓸 수 있음 | 파싱·상수·배치·인코딩 성공 후에 출력 파일 열기 |

일반 함수와 결과 구조체를 단계별로 구성하고, `err`와 `is_success`로 실패 위치를 전달했다. 각 설계의 동작 규칙은 [SPECIFICATION.md](SPECIFICATION.md), 검증 입력과 결과는 [RESULTS.md](RESULTS.md)에 연결했다.

## 시작 상태

2026-11-28 기준 기존 코드에는 소스 읽기, 파싱, 정수·문자·레지스터·메모리 피연산자 해석, 타입별 인코더, 상수 수집, 명령어·지시어 크기 계산이 있었다. 이 중 명령어 표, CSR 인코더, 일부 오류 처리는 앞선 대화에서 AI가 도왔다. `main`은 파싱 결과를 출력하는 상태였다.

이후 남은 통합 구현은 AI 작성 에이전트가 맡고, 검토 에이전트가 별도의 검사와 수정 요청을 수행하는 방식으로 진행했다. 기존 구현과 AI가 추가·수정한 범위는 이 문서의 작성 이력과 [AI_USAGE.md](AI_USAGE.md)에 구분했다.

초기에는 설명과 검토를 받으며 사용자가 함수를 작성했다. 중간에 일괄 AI 구현을 요청했다가 되돌리고, 기존 `2ce596c` 시점의 작업을 바탕으로 인코더 구현을 계속한 과정도 있었다. 최종 완성 작업에서는 그때의 백업 구현을 재사용하지 않고 현재 코드에서 이어 작성했다.

사용자는 명령어 표 채우기, CSR 인코더, 상수 수집의 일부 반복적인 오류 처리, 가상·실제 명령어 이름 확인, 지시어 검증 보완을 따로 요청했다. 따라서 초기 커밋 전체를 사용자 단독 작성으로 분류하지 않는다.

## 초기 구현에서 확인하고 고친 문제

| 문제 | 확인한 원인과 수정 방향 |
|---|---|
| `std::transform` 호출 오류 | 변환 결과를 저장할 시작 위치 인수가 빠져 있어 `begin()`을 출력 위치로 추가 |
| 16진수와 정수 오버플로 | 자리 값을 더하기 전에 한계값을 검사하고, 음수 최솟값의 크기도 처리 |
| 음수 즉시값 조립 | 절댓값으로 바꾸지 않고 부호 없는 값으로 변환한 뒤 필요한 비트만 마스킹 |
| `.equ` 이름 검사 | 반복문에서 계속 `name[0]`을 검사하던 부분을 현재 문자 `name[i]` 검사로 수정 |
| `.equ` 등록과 오류 | 이름 중복 검사와 실제 상수 맵 등록을 구분하고, 잘못된 정의를 조용히 건너뛰지 않고 줄 번호와 함께 실패 처리 |
| 문자열·쉼표 처리 | 문자열 안의 쉼표·주석 기호와 이스케이프된 따옴표를 일반 구분자로 오인하지 않도록 확인 |
| `.space`·`.align`의 없는 상수 | 다른 분기에서 가져온 8바이트 성공 반환을 오류 반환으로 변경 |
| 지시어 반환형 축소 | `.space 2147483648`이 음수 크기로 성공하고 `.align 32`도 음수로 반환되는 현상을 재현한 뒤, `INT_MAX` 검사 후 변환하도록 수정 |
| 문자열 지시어 입력 | 빈 피연산자, 큰따옴표가 없는 값, 미지원 이스케이프, 여러 문자열을 검사 |
| 함수 반환 누락 | 크기 0인 지시어 처리와 알 수 없는 지시어의 마지막 오류 반환 추가 |

이 표는 대화와 코드 검토에서 확인되는 시행착오의 요약이다. 과거 모든 실행의 원본 로그가 남아 있는 것은 아니며, 최종 검사 결과와 보존한 실행 출력은 [RESULTS.md](RESULTS.md)에 구분했다.

## 대표 문제의 원인 분석과 수정

### 1. 내부 계산이 맞아도 반환형에서 크기가 손상되는 문제

`.space`와 `.align`을 검사할 때 계산 과정뿐 아니라 최종 반환형까지 확인할 필요가 있었다. 내부에서는 64비트 값으로 계산했지만 반환 구조체의 `byte_size`가 `int`여서, 큰 값이 음수로 바뀐 뒤 성공으로 반환되는 현상이 발생했다.

| 재현 입력 | 수정 전 확인한 결과 | 수정 후 처리 |
|---|---|---|
| `.space 2147483648` | -2147483648바이트로 성공 | `INT_MAX` 초과 오류 |
| 주소 `0x10000`의 `.align 32` | -65536바이트로 성공 | 추가할 크기의 `INT_MAX` 초과 오류 |

수정에서는 64비트로 크기를 계산한 뒤 반환 가능한 범위인지 먼저 검사하고, 통과한 값만 `int`로 변환했다. 이 원칙을 `.byte`·`.half`·`.word`의 항목 수 계산에도 적용했다. 최종 빌드에서는 정수 축소 변환과 반환 누락을 오류로 취급하고, 자동 검사에서는 큰 크기와 잘못된 정렬 인수를 다시 확인했다.

### 2. 크기 계산 성공이 올바른 입력을 뜻하지 않는 문제

문자열 지시어의 초기 구현은 첫 번째와 마지막 문자를 제외하고 길이를 세는 방식이어서 `.ascii 123`을 1바이트로 받아들였고, `\q`도 일반 문자처럼 계산했다. 피연산자가 없을 때의 접근이나 두 번째 문자열을 무시하는 경우도 검토 대상이었다.

입력 개수, 큰따옴표 형식, 본문의 따옴표와 이스케이프를 검사하도록 보완했다. 최종 통합에서는 `parse_string_literal()`의 해석 결과를 크기 계산과 바이트 생성에 함께 사용하여 두 단계가 같은 문자열을 다르게 해석할 가능성을 줄였다. 빈 문자열, 알려진 이스케이프, 잘못된 문자열 입력은 자동 검사에 포함했다.

### 3. 테스트가 구현 요구보다 좁은 형식을 가정한 문제

첫 통합 검사에서는 listing의 global 표시 `G`가 심볼 이름 뒤에 와야 한다고 테스트가 가정하여 실패했다. 실제 출력에는 주소·영역·global 표시·이름이 모두 있었으며, PDF는 그 정보의 제공을 요구했다.

요구사항을 다시 대조한 뒤 검토자가 표시 순서에 의존하지 않도록 테스트를 수정했다. 구현자가 통과를 위해 기대값을 임의로 바꾸지 않도록 검토와 수정을 구분했고, 수정한 검사로 전체 16개 테스트 메서드가 통과하는 것을 확인했다.

## 과제 조건 정정

사용자가 전달한 교수님 답변에 따라 PDF 11쪽의 `jal label → jal a0, label`을 `jal label → jal ra, label`로 수정하여 해석했다. `jal FUNC`와 함수 끝의 `ret`이 같은 복귀 주소 레지스터 `ra`를 사용하도록 하는 규칙이다. 예제 소스의 호출 명령은 바꾸지 않았다.

## 실제 사용자 요청

남은 구현을 맡긴 요청:

> 그냥 나머지도 딱 내 코드 수준으로 너가 짜주면 안돼 완성까지? 너무 힘든데

이후 구현 방식에 대해 사용자는 구현 에이전트 하나에 기존 스타일과 자주 틀린 부분을 전달하고, 검토와 수정을 반복하도록 요청했다. 전체 대화 원문과 이 요약은 별개이며, 과제 제출에 전체 원문이 필요하면 해당 대화를 함께 보관해야 한다.

## 구현 에이전트에게 전달한 작업 지시 요약

- 기존 코드를 보존하면서 남은 섹션·주소 계산, 가상명령 변환, 데이터 생성, 출력과 `main`을 완성한다.
- 일반 함수, 단순 구조체, `_rtn`, `err`와 `is_success`, `if/else`, 반복문, `set`·`unordered_map`을 사용한다.
- 불필요한 클래스·템플릿·일반화 구조를 추가하지 않는다. 문자열이나 구조체 복사 같은 기존 방식은 성급하게 최적화하지 않는다.
- 이전 실수는 의도적으로 따라 하지 않고 검사 항목으로 삼는다: 빈 피연산자 접근, 잘못된 인덱스, 누락된 반환, 중복 이름, 없는 심볼을 성공으로 처리, 정수 축소·오버플로·시프트 범위, 따옴표와 이스케이프, 배치와 실제 출력 크기의 불일치.
- 교수님 정정인 `jal label → jal ra, label`을 적용하고 제공 예제를 수정하지 않은 채 처리한다.
- AI 작성 범위를 기록하고, 검토자가 실제로 확인한 결과만 보고한다. Git 커밋·push는 사용자가 실행한다.

이 절은 작업 지시의 요약이며, 보존한 프롬프트는 [PROMPTS.md](PROMPTS.md)에서 확인할 수 있다.

## 작성과 검토

1. 구현 에이전트가 기존 파서·인코더에 연결할 값 해석, 명령어 변환, 배치, 출력 함수를 작성했다.
2. 검토 에이전트가 PDF를 읽고 요구사항을 확인했다. `.word`의 비정렬 저장 허용, data 끝에서 바이너리가 끝나는 규칙, 피연산자 없는 `fence`, 섹션 전환 줄의 라벨 보존을 전달했다.
3. 검토 에이전트가 실제 인코딩과 배치를 기준으로 `tests/test_assembler.py`를 작성했다. 구현 에이전트가 검사에 맞춰 기대값을 변경하지 않도록 역할을 분리했다.
4. 검토 중 `: nop`과 `:`가 빈 라벨로 통과하는 문제가 발견되어 `read_source`에서 줄 번호를 포함한 오류로 처리했다.
5. 첫 출력 코드의 임시 파일·백업 교체 구조가 기존 코드 수준보다 복잡하다는 지적을 받아 단순 `ofstream` 기록으로 정리했다. 소스 분석·기계어 생성은 출력 파일을 열기 전에 모두 끝낸다.
6. 최초 전체 검사에서 listing의 `G` 표시와 이름의 열 순서에 대한 검사 가정이 실제 요구사항보다 좁다는 점을 검토자가 확인했다. 검토자가 검사를 수정했으며 실제 global 표시는 유지했다.
7. 최종 사용성 검사에서 `build.ps1`이 PowerShell 실행 정책에 막히는 문제가 확인됐다. 시스템 정책을 바꾸는 대신 `build.cmd`를 추가하고 Windows 기본 빌드 안내를 변경했다.

## 추가한 범위

AI 작성 에이전트는 `value`, `instruction`, `layout`, `output` 파일과 최종 `main`, 빌드 안내를 추가했다. 기존 `assembler`에 수식 계산을 연결하고, `operand`의 빈 입력·정수 경계·문자 검사와 메모리 피연산자 처리를 보완했다. 기존 `encoder`에는 명령어 형식 조회 함수를 추가했다. 검토 에이전트는 예제 추출, 테스트 코드, 독립 실행 검사와 수정 요청을 담당했다.

## 검증 방법

```text
g++ -std=c++17 -O2 -Werror=narrowing -Werror=return-type main.cpp assembler.cpp parser.cpp operand.cpp encoder.cpp value.cpp instruction.cpp layout.cpp output.cpp -o assembler.exe
python tests/test_assembler.py ./assembler.exe
```
